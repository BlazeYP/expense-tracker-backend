01 · Transactions

Browse stored transactions, inspect one record, or adjust its category assignment.

GET/api/v1/transactions

List every transaction currently stored.

Request

No body or query parameters.

Response

JSON array of transaction records. Each record includes:

id, source, transactionDateTime, type (DEBIT/CREDIT), amount, currency, description, upiTransactionId, importBatchId, nested counterparty, account, category, categorization, deduplicationHash, originalData, createdAt, updatedAt.
GET/api/v1/transactions/{id}

Fetch the full transaction record for one ID.

Request

Path parameter id. No body.

Response

One transaction object, with the same fields as the list response. Unknown ID returns 404 with {"error":"Transaction not found"}.

PATCH/api/v1/transactions/{id}/category

Set a user's chosen category on a transaction. This marks the categorization as manually overridden.

Request

Path parameter id; JSON body:

{"categoryId":"<active-category-id>"}
Response

Updated transaction object. Its category source is MANUAL, confidence is 1, and manuallyOverridden is true. Transaction or active category missing → 404.

POST/api/v1/transactions/{id}/recategorize

Run the categorization logic again using merchant mappings, rules, then a fallback category.

Request

Path parameter id. No body.

Response

Updated transaction object with refreshed category and categorization details. An existing manual override is preserved by the categorizer.

POST/api/v1/transactions/recategorize

Recategorize transactions with a missing category or the DEFAULT source, using current merchant mappings and active rules.

Request

No body or query parameters.

Response

Counts for scanned, assignedByRule, assignedByMerchant, and leftAtDefault. Categories that remain unmatched keep the configured fallback category. Manually assigned and AI categories are not selected.

POST/api/v1/transactions/ai-recategorize

Ask the configured LLM to categorize a bounded batch of stored transactions. Manual overrides are always skipped.

Request

Optional JSON body; omitted fields use the shown defaults. limit is capped by server configuration (100 by default).

{
  "limit": 100,
  "minimumConfidence": 0.7,
  "dryRun": true,
  "onlyDefaultCategory": true
}

By default, only fallback/default-category transactions are candidates. Set onlyDefaultCategory false to include rule/merchant categories. dryRun returns suggestions without writing.

Response
{
  "scanned": 20,
  "processed": 20,
  "updated": 0,
  "proposed": 17,
  "skipped": 2,
  "failed": 1,
  "dryRun": true,
  "results": [{
    "transactionId": "<id>",
    "categoryId": "<active-category-id>",
    "categoryName": "Dining",
    "confidence": 0.91,
    "reason": "Restaurant merchant",
    "status": "PROPOSED"
  }]
}

Statuses are UPDATED, PROPOSED, LOW_CONFIDENCE, or FAILED. Only valid active category IDs above the confidence threshold are saved; saved categories use source AI. AI must be enabled and configured, otherwise the endpoint returns 503.

Transaction subobjects: counterparty carries originalName, normalizedName, upiId; account has accountId, bankName, last4; category has categoryId, categoryName, source (including AI), ruleId, confidence, manuallyOverridden, and optional reason. categorization has source, ruleId, confidence, categorizedAt.

02 · Statement import

Upload one Google Pay statement. This endpoint consumes multipart form data, not JSON.

POST/api/v1/imports/gpay

Parse a GPay CSV or PDF statement, deduplicate transactions, categorize new records, and report import totals.

Request

Content-Type: multipart/form-data; one required part named file. Accepted formats: GPay CSV/PDF. Maximum file/request size: 15 MB.

curl -X POST http://localhost:8080/api/v1/imports/gpay \\
  -F 'file=@statement.pdf;type=application/pdf'
Response

Import batch object:

{
  "id": "<batch-id>",
  "source": "GPAY",
  "fileName": "statement.pdf",
  "fileHash": "<sha256>",
  "statementPeriodStart": "2026-03-01",
  "statementPeriodEnd": "2026-08-31",
  "status": "COMPLETED",
  "totalRows": 42,
  "parsedRows": 40,
  "importedRows": 38,
  "duplicateRows": 2,
  "failedRows": 0,
  "errors": [],
  "startedAt": "2026-09-01T10:00:00Z",
  "completedAt": "2026-09-01T10:00:03Z",
  "createdAt": "2026-09-01T10:00:00Z"
}

Period fields may be null when unavailable. Status is PROCESSING, COMPLETED, PARTIAL_SUCCESS, or FAILED. Re-uploading the same file returns its previous batch unless that batch failed.

03 · Analytics

Aggregate transaction amounts for an inclusive calendar-date range.

GET/api/v1/analytics/summary?from={date}&to={date}

Return debit/credit totals, net flow, transaction count, and amount by category.

Request

Required query parameters from and to as ISO dates (YYYY-MM-DD). to must be on or after from. Date boundaries use configured business timezone (default Asia/Kolkata).

GET /api/v1/analytics/summary?from=2026-03-01&to=2026-08-31
Response
{
  "from": "2026-03-01",
  "to": "2026-08-31",
  "transactionCount": 42,
  "debits": 12500.00,
  "credits": 9000.00,
  "net": -3500.00,
  "amountByCategory": {
    "Food": 3200.00,
    "Uncategorized": 450.00
  }
}

net = credits − debits. The category map includes both debit and credit amounts; missing category names are grouped as Uncategorized.

GET/api/v1/analytics/monthly?year={year}

Return gross transaction amount, debit total, and credit total for each month in the requested calendar year.

Request

Required query parameter year (1–9998). Month boundaries use configured business timezone (default Asia/Kolkata). All 12 months are included; months without transactions have zero totals.

GET /api/v1/analytics/monthly?year=2026
Response
{
  "year": 2026,
  "months": [
    {
      "month": 1,
      "monthName": "JANUARY",
      "totalTransactionAmount": 1500.00,
      "totalDebits": 1200.00,
      "totalCredits": 300.00
    }
  ]
}

totalTransactionAmount is the sum of debit and credit transaction amounts. The months array contains all calendar months in order.

04 · Categories

Maintain the category taxonomy used for labeling transactions.

GET/api/v1/categories

List all category records (active and inactive).

Request
No body or parameters.
Response
JSON array of category objects.
POST/api/v1/categories

Create a category.

Request

JSON category fields:

{
  "name": "Dining",
  "description": "Restaurants and cafes",
  "transactionType": "DEBIT",
  "parentCategoryId": null,
  "active": true,
  "systemDefined": false
}

name is required and cannot be blank. Server assigns ID and timestamps.

Response
Created category object with id, submitted fields, and createdAt/updatedAt. Blank name → 400.
PUT/api/v1/categories/{id}

Replace editable category properties for an existing category.

Request

Path id; JSON fields name, description, transactionType, parentCategoryId, active. Treat as a full update because omitted values are assigned from the request object.

Response
Updated category object. Missing ID → 404.
DELETE/api/v1/categories/{id}

Deactivate the category (soft delete); the record remains in storage.

Request
Path id. No body.
Response
Empty response body on success. Missing ID → 404.
Category object: id, name, description, transactionType, parentCategoryId, active, systemDefined, createdAt, updatedAt.

05 · Merchants

Map a normalized counterparty name and aliases to a default category.

GET/api/v1/merchants

List all merchant records.

Request
No body or parameters.
Response
JSON array of merchant objects.
POST/api/v1/merchants

Create a merchant mapping.

Request
{
  "originalName": "Acme Foods Pvt Ltd",
  "defaultCategoryId": "<category-id>",
  "aliases": ["Acme Foods", "Acme Cafe"],
  "active": true
}

originalName is required; normalizedName is generated from it. ID is generated by the server.

Response
Saved merchant object including generated id, normalized name, and timestamps. Blank name → 400.
PUT/api/v1/merchants/{id}

Save merchant data under the supplied ID (upsert-style repository save).

Request
Path id; JSON fields originalName (required), defaultCategoryId, aliases, active. Normalized name is recalculated.
Response
Saved merchant object including its ID and timestamps.
Merchant object: id, originalName, normalizedName, defaultCategoryId, aliases (string array), active, createdAt, updatedAt.

06 · Categorization rules

Apply conditional matches to assign a category, ordered by ascending priority.

GET/api/v1/rules

List all categorization rule records.

Request
No body or parameters.
Response
JSON array of rule objects.
POST/api/v1/rules

Create a rule. At least one condition and a category ID are required.

Request
{
  "name": "Coffee shops",
  "categoryId": "<category-id>",
  "transactionType": "DEBIT",
  "priority": 20,
  "active": true,
  "conditions": [
    {"field":"DESCRIPTION", "operator":"CONTAINS", "value":"coffee"}
  ]
}

Supported fields: DESCRIPTION, COUNTERPARTY_NAME, NORMALIZED_MERCHANT, UPI_ID, TRANSACTION_TYPE, AMOUNT. Operators: EQUALS, CONTAINS, STARTS_WITH, ENDS_WITH, REGEX. All conditions in a rule must match.

Response
Saved rule object with generated id and timestamps. Missing category ID or empty conditions → 400.
PUT/api/v1/rules/{id}

Save rule fields under the supplied ID (upsert-style repository save).

Request
Path id; JSON rule shape as above: name, categoryId, transactionType, priority, active, conditions. The create-only validation is not repeated here.
Response
Saved rule object.
DELETE/api/v1/rules/{id}

Permanently delete a rule by ID.

Request
Path id. No body.
Response
Empty response body on success.
Rule object: id, name, categoryId, transactionType, priority (default 100), active (default true), conditions (array of {field, operator, value}), createdAt, updatedAt. Merchant matches are checked before rules; rules are checked in priority order.

07 · Accounts

Maintain bank/account metadata used by the application.

GET/api/v1/accounts

List all account records.

Request
No body or parameters.
Response
JSON array of account objects.
POST/api/v1/accounts

Create an account record.

Request
{
  "provider": "UPI",
  "bankName": "Example Bank",
  "accountType": "SAVINGS",
  "last4": "1234",
  "currency": "INR",
  "active": true
}

All fields are optional in the controller/model. last4 is normalized to digits and truncated to the last four; timestamps and ID are set by the server.

Response
Saved account object.
PUT/api/v1/accounts/{id}

Update an existing account.

Request
Path id; JSON fields provider, bankName, accountType, last4, currency, active. Send the complete editable representation: values are copied as supplied.
Response
Updated account object. Missing ID → 404. Unlike create, update does not normalize last4.
Account object: id, provider, bankName, accountType, last4, currency (default INR), active (default true), createdAt, updatedAt.

Errors & conventions

Shared behavior from the API exception handler and application configuration.

Common error payload

{"error":"Human-readable explanation"}

Validation/argument errors and duplicate-key errors return 400; missing resources explicitly checked by controllers return 404; oversized upload returns 413; unexpected server errors return 500 with a generic message. Invalid analytics date order is a 400.

  • All routes use /api/v1. JSON endpoints accept and return JSON unless specified.
  • Collection GET routes currently return all records; pagination and filtering are not defined.
  • Model fields are returned directly, including nested model fields and server-managed metadata.
  • Import duplicate-file detection uses the uploaded file hash. Individual transaction deduplication is also performed.
  • API calls from localhost and 127.0.0.1 origins are allowed by the current CORS configuration.
